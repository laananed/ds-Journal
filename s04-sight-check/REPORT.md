## 4. 问题清单（按日常影响排序）

### P1（输入丢失，应先修）Insight 编辑时刷新/关页会静默丢失输入

- 复现：洞察 → 打开任一条 → 修改 → 输入文字 → 800ms 内按 F5（或关闭标签页）。
- 实测：`PATCH 次数 0`；服务器正文不含新输入；重新打开页面也不显示；页面上无任何草稿恢复提示或离开提醒（`insight-reload-results.json`）。
- 原因（只读代码得出）：`InsightPage` 只依赖 800ms 防抖自动保存，既不注册 `beforeunload`（Journal 的 `useAutosave` 有），也不写本地草稿（`insightSession` 明确「不为本地草稿扩域」，`useJournalDraftMirror` 仅 Journal）。
- 影响：普通「边写边想起要刷新/手滑 F5/关标签」就会丢掉最后一段输入，且没有任何提示；与 Journal 的保护等级不一致，用户会以为 Insight 同样安全。
- 说明：这是**输入丢失**，不是保存失败提示缺失。

### P2（输入丢失，中）日程新建/编辑表单没有未保存保护

- 复现：日程 → 新建日程 → 填标题与时间 → 刷新页面（或关闭标签页）。
- 实测：`beforeunload` 未被拦截，刷新后表单关闭、输入不恢复、无提示（E1）。
- 对照：同一份输入在「模块内切走」时有确认对话框（E2 通过），说明缺失的是浏览器级离开保护。
- 影响：日程表单内容较短，但时间与标题都要重填；属于静默丢失。
- 备注：日程没有本地草稿能力，属于设计选择；至少应有 `beforeunload` 级别的提醒。

### P3（语义不符，中低）Insight「取消新建」仍会把内容保存成新文件

- 复现：洞察 → 新建 Insight → 填标题和正文 → 点「取消新建」。
- 实测：`POST /api/insights` 1 次（标题同提交内容），服务器已生成新 Insight（E4）。
- 原因：按钮走 `onNavigate(showList)`，导航前统一 flush 会先保存；加上 800ms 自动保存，点击前往往已经创建。
- 影响：用户以为「放弃这份草稿」，结果列表里多出一条不想要的记录，需要再删除一次。不是数据丢失，但违背按钮承诺，容易让人误判「取消没生效」。

### P4（提示不一致，低）日程创建成功后列表刷新失败，新条目不在列表里

- 复现：日程 → 新建 → 保存成功 → 紧接着列表 GET 失败（断网/后端重启）。
- 实测：出现「已创建日程（不影响 Set 目标）。」+「网络中断，暂时无法读取日程列表。」横幅，但列表仍是旧的 2 条，看不到刚创建的条目；服务端实际已创建（E3）。
- 影响：用户可能重复创建同一条日程。建议创建成功后把服务器返回的资源直接插入列表（编辑已有 `replaceItem`，创建缺一个 `insertItem`）。

### 非问题（已核对，供参考）

- 日程创建键重放、删除 `If-Match`、编辑只提交变化字段，均与 `backend/app/schedule` 契约一致。
- 搜索/链接点击都会先读目标再跳转，404 有明确提示，不存在「点了没反应」。
