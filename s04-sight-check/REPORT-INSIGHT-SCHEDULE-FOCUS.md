## 1. Insight 输入后立即刷新 / 关闭

每个场景独立上下文。`间隔` 为「最后一次输入 → 导航开始」的实测毫秒。

### 1.1 新建记录（标题 + 正文）

| 场景 | 间隔 | POST | 本地草稿 | 刷新后可见 | 离开提示 |
| --- | --- | --- | --- | --- | --- |
| 立即刷新 | 76ms | 0 | 无（idb 空） | 否 | 无 |
| 等 400ms 刷新 | 493ms | 0 | 无 | 否 | 无 |
| 等 1200ms 刷新 | 1267ms | 1 | 无 | **是**（列表 + 正文都在） | 无 |
| 输入后关闭页面 | — | 0 | 无 | 否 | 无 |

### 1.2 已有记录（追加正文）

| 场景 | 间隔 | PATCH | 本地草稿 | 刷新后可见 | 离开提示 |
| --- | --- | --- | --- | --- | --- |
| 立即刷新 | 68ms | 0 | 无 | 否 | 无 |
| 等 400ms 刷新 | 478ms | 0 | 无 | 否 | 无 |
| 等 1200ms 刷新 | 1265ms | 1 | 无 | **是** | 无 |
| 输入后关闭页面 | — | 0 | 无 | 否 | 无 |

稳定复现条件：新建与已有记录都一样——**在最后一次输入后的约 0.8s 防抖窗口内刷新或关闭**，输入必丢，且服务端、浏览器本地、刷新后的页面三处都没有痕迹。窗口外（约 1.2s）正常落库。

补充事实：

- 编辑器右下角有「未提交到服务器 / 仍在编辑器中，尚未提交到服务器」的状态，但这是**刷新前**的提示；刷新后没有任何恢复入口或「上次有未保存内容」的提示。
- 仅输入标题、正文为空时，即使等过防抖也不会创建（`insightDraftIssue = 'blank'` → `blocked`），这条属于既有设计（提示「空白输入不会提交」），不是本轮的丢失缺陷，但会与「取消新建」的提示混淆（见 §2）。

判定：**失败（P1，静默丢失输入）**，新建与已有记录都命中。

## 2. Insight「取消新建」

按钮文案与实际行为在三种输入下都不一致：

| 输入 | 点击「取消新建」后 | POST | 是否生成记录 | 面板 |
| --- | --- | --- | --- | --- |
| 空内容 | 弹出「**最新改动还没保存成功，确定离开？**」+「自动保存失败或出现版本冲突…」 | 0 | 否 | 需点「确认离开」才关闭 |
| 仅标题（无正文） | 同上，同样的「保存失败」文案 | 0 | 否 | 需点「确认离开」才关闭；标题被丢弃 |
| 有正文 | **不弹任何对话框**，直接离开 | 1 | **是**，生成 `未命名 Insight` 或带标题记录 | 关闭，列表出现新条目 |

根因（代码 + 实测定位，未修改）：新建面板一挂载，会话就被判为「有未提交输入」——**不输入任何内容、等待 1s，状态条仍是「未提交到服务器」（`autosave-unsaved`），且没有发出任何写请求**（见 `cancel-initial-state.json`）。此时点「取消新建」，`guardedSave` 会先命中 `issue === 'blank'` 并返回 `blocked`，App 便按「保存失败」弹出 `leaveBlocked` 对话框；有正文时 `issue === ''`，`flush` 真正 `POST` 成功后才导航，于是「取消」变成了「创建并离开」。状态判定走 `draftEquals(draft, baseline)`，说明新建面板的 draft 与 baseline 从挂载起就不相等（很可能是编辑器挂载时文档规范化触发了一次草稿变更），未再拆到具体字段。

影响：普通用户新建 Insight 后想放弃，会连续遇到两种相反的错误——要么被一句假的「保存失败」拦住（空/仅标题），要么被静默创建一条真实记录（有正文）。后者会污染列表，且没有任何「已创建」提示。

判定：**失败（P3，按钮语义与行为不一致 + 误导性错误文案）**。

## 3. 日程编辑时刷新 / 关闭

| 场景 | 离开提示 | 请求 | 刷新后 | 草稿恢复 |
| --- | --- | --- | --- | --- |
| 编辑已有，改标题后立即刷新（70ms） | 无 | PATCH 0 | 表单关闭，列表仍为原标题 | 无 |
| 编辑已有，改标题后关闭页面 | 无 | PATCH 0 | —（服务端仍原标题） | 无 |
| 编辑已有，点「保存」成功后刷新（对照） | — | PATCH 1 | 新标题保留，表单关闭 | 不适用（已确认保存） |
| 新建表单填标题+时间后立即刷新 | 无 | POST 0 | 表单关闭，列表无新条目 | 无 |
| 编辑中站内切换模块（对照） | **有**：「当前内容尚未保存，确定离开？」 | — | 仍停在日程表单 | 不适用 |

结论：**站内导航有保护，浏览器刷新/关闭完全没有**。未提交的表单（新建与编辑）在刷新/关闭时静默丢失；已经点过「保存」并看到「已保存修改。」的内容则正常持久化——两者边界清晰，问题只在未提交态。

判定：**失败（P2，未提交表单在刷新/关闭时无提示、无草稿）**。已确认保存的内容不受影响（通过）。

## 4. 日程创建成功、随后列表刷新失败

复现：列表正常加载（2 条）→ 注入 `GET /api/schedules` 500 → 新建「刷新失败MSF」并保存。

| 观测点 | 实测 |
| --- | --- |
| 请求序列 | `POST /api/schedules`（201）→ `GET /api/schedules?page=1`（500） |
| 服务端记录数 | 2 → **3**（新记录确实写入） |
| 成功提示 | 「已创建日程（不影响 Set 目标）。」 |
| 列表内容 | 仍是旧的 2 条，**不含新条目** |
| 失败横幅 | `internal error` + 「下面显示的是最近一次成功读取的列表…不会重复发送删除或保存。」+「重新读取」 |
| 表单 | 已关闭 |

重复创建风险实测：由于表单已关闭、成功提示又说「已创建」，用户若再点「新建日程」重填同名日程：

- 两次 POST 的 `client_create_id` 不同（`e285bd94…` / `e09e8c72…`），幂等键不复用；
- 服务端变成 **4 条，其中同名 2 条**；
- 点「重新读取」后列表显示 4 条，两条重复都可见。

也就是说：只要用户没先点「重新读取」，重试就会产生重复记录；界面没有任何「这条可能已经创建成功，请先重读」的提示，横幅正文还是英文 `internal error`。

判定：**失败（P4，提示与列表不一致，存在重复创建路径）**。若用户先点「重新读取」再操作，则不重复（通过）。

## 6. 未验证 / 边界

- 真实后端与网络栈：`keepalive`、请求在导航瞬间被中断时服务端是否收到、CORS 预检均未测（本轮全部为 Mock 同源）。
- 真实浏览器关闭窗口的原生提示：headless 下用 `runBeforeUnload` 模拟，未验证真实 Chrome 的 UI 呈现；但方法学对照已证明提示可被捕获。
- 0.8s 临界点未逐毫秒界定（只测了 493ms 丢、1267ms 保），且受输入法、机器负载影响。
- 中文输入法组合期输入、多标签并发、移动端、读屏与视觉验收未覆盖。
- Insight 标题为空、正文非空时取消会创建 `未命名 Insight`，属预期命名规则，未视为缺陷。
