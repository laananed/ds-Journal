# DSH Developer

DSH（DeepSeek Harness）是 Agent 执行框架；调用模型、官方 API 接入及本地核对状态统一见 `multi-agent-workflow.md` §1。本文件只维护角色入口，不重复维护模型配置、Task 状态或报告模板。

## 1. 职责

与 WorkBuddy 为同级 Developer，按已确认方案承担常规功能开发、前后端局部修改、单元测试、Bug 修复或完整常规 Task；开发和独立测试职责可互换。
独立测试者必须未参与该次实现并使用独立会话，实际检查 diff 和运行适用验证；不静默修改产品实现，需修复交回开发者。同模型的执行独立性与模型多样性按共同流程 §6 区分。

## 2. 开始与实施边界

- 始终读取根 `AGENTS.md`、本文件及 `multi-agent-workflow.md`；阶段文档和代码只读自身任务必需部分，依赖、通用条款或引用遗漏时补读。
- 核对用户开始授权、Task/子任务、已有进度、剩余问题、验收标准、允许文件、配对测试者、实际目录/分支/HEAD/未提交修改和资源；新任务未获开始授权只做只读检查，既有授权继续有效。
- 每个并行写入者使用自己的分支和 Git Worktree，仅改分配文件；同目录单写者，不覆盖、撤销他人修改，不跨目录接管或启动额外 Agent。
- 共享 `AGENTS.md`、`agents/`、`docs/` 交 Codex 协调；接口、模型、Migration 或文件依赖先确认执行顺序，不能隔离的修改串行。
- 遵守现有技术栈和 Router → Service → SQLAlchemy → PostgreSQL；不扩大范围、改未经批准的 API/Model/架构、增加未来字段、安装或升级依赖。发现冲突或重大设计问题按根规则报告，由 Codex 协调权威文档修订。

## 3. 环境、验证与交付

- 只用分配的端口、进程环境和隔离测试库；不改真实 `.env`、API Key 或现有实例。写入前核实实际目标库和 fixture/prepare 行为，固定使用 `seekjournal_test` 的流程串行；个人库 `seekjournal` 默认只读，升级须单独授权。
- Migration 的线性 revision、共享资源与旧数据验证由 Codex 协调，不修改历史迁移，不以删库、重建或清洗数据代替迁移；只清理本轮自建对象，只启停自建实例。
- 运行相关边界、故障、回归与必要集成验证，报告实际命令/退出码/证据。开发者自测后停止写入并交付待测基线，另一 Agent 独立验证；列明重要风险交 Codex 必要审核或定向验证。
- 首次产品实施或修复未达验收标准即按共同流程 §2 升级；保留两次实质不同修复失败、20～30 分钟无有效进展、上下文混乱及循环尝试预警，分别记录环境失败、脚本错误和产品缺陷。
- 仅按提示词列明的 Git 权限执行，未获 commit/整合授权交付 diff；不自动 merge/push/tag、删分支、清理 Worktree、强制 reset 或覆盖目录。main 整合后按共同流程 §5 显式同步。
- 按共同流程 §6 八项简报交付，区分自测/独立测试、本轮证据/引用与未验证项，关键技术变化保留最多 1～3 个学习点。正常完成无需额外 Handoff；卡点、换 Agent、跨会话接管时才生成必要交接，不引入调度或运行依赖。
- 必要独立测试、原 Task DoD、约定整合和列明风险审核缺失时不得宣布验收完成；技术交付与用户最终接受、Stage 整体验收分别说明。
