# SeekJournal Multi-Agent Workflow

本文件维护 Agent 配置、任务规划、Git/Worktree 协作与统一验收流程。
产品/API/架构/Task 分别引用根 `AGENTS.md` 指定的阶段文档；规划不构成实施授权，历史执行记录不代表当前状态。

## 1. 当前配置与职责

| Agent / 执行端 | 模型与接入 | 职责入口 |
|---|---|---|
| Codex / Codex App 或 CLI | GPT-6.1-Sol | Lead、架构与重要决策、任务分析/拆分/分配、复杂实现、疑难接管、必要风险审核与 Git 整合协调；`gpt-lead.md` |
| WorkBuddy / WorkBuddy 客户端 | 保留现行 DeepSeek V4.1 Flash 配置；客户端 ID `deepseek-v4.1-flash`，本地核对状态见下 | 常规开发与独立测试；`ds-developer.md` |
| DSH / DeepSeek Harness | DeepSeek V4.1 Flash，经 DeepSeek 官方 API；推荐官方 ID `deepseek-flash`，本地仍使用兼容 ID，见下 | 常规开发与独立测试，与 WorkBuddy 同级；`dsh-developer.md` |

DSH 是 Agent 执行框架，DeepSeek V4.1 Flash 是其调用的模型；不能把执行框架名称当作模型名称。模型和执行端信息只在本节维护，角色文件与提示词引用它。

User 是 Product Owner，决定产品方向、批准重大变化和开始实施，并最终接受交付。
这是项目角色与额度分配策略，不是未经验证的模型性能排名。Codex 被调用时负责 Lead 决策、必要审核、升级处理与整合协调，共享规范及权威文档仍由 Codex 维护；常规技术交付可由开发者与独立测试者完成。

最多三个 Agent 同时开发，包含正在写代码的 Codex；日常优先两个。用户已批准三路并发能力，有三个可独立执行的工作项且文件、分支/Worktree、端口、数据库、进程及测试资源隔离满足时可安排三路，不重复申请人数许可。每个具体 Task 仍须 §3 的只读检查、依赖分析、资源分配与用户确认开始；本轮配置授权不启动额外 Agent、不授权新 Task。独立测试同样遵守资源隔离和同目录单写者规则；不引入任务调度服务、自动编排框架或新的运行依赖，不擅自调用或创建其他 Agent。

| 模式 | 安排与使用条件 |
|---|---|
| A | WorkBuddy + DSH 并行开发独立工作项，Codex 协调与必要审核；相互独立测试在各自待测基线交付后进行 |
| B | Codex + WorkBuddy + DSH 三路开发互不冲突的子任务；每项仍指定未参与该项实现的独立测试者，并安排测试资源时段 |
| C | 共享文件、数据库迁移、跨模块接口或测试资源存在依赖时，明确串行链，其他独立工作项可并行 |

## 2. 分配原则

每个 Task / 子任务有明确输入、输出、允许文件、验收标准和交接方式。Codex 综合判断：

| 因素 | 要判断的问题 |
|---|---|
| 任务依赖 | 前置产出是否就绪，哪些必须串行、哪些可以独立执行？ |
| 技术风险 | 是否涉及迁移、数据一致性、核心架构或跨模块改动，需要哪些审核点？ |
| 模型能力 | 哪个 Agent 更适合该项分析/实现/调试工作，既有上下文是否有用？ |
| 并行效率 | 扣除交接、等待、冲突与整合成本后，是否减少总体时间？ |
| 文件冲突 | 是否能在独立 Worktree 修改不同文件，共享入口如何安排？ |
| 成本效率 | 在质量达标前提下如何使用已有额度，避免重复开发/无收益拆分？ |
| 可验证性 | 产出和通过条件是否清楚，能否提供实际测试证据？ |

- 常规任务优先交给 WorkBuddy 或 DSH，选择已有上下文、能力适配与额度更合适的一方；默认一方开发、另一方独立测试，可互换，不强制平均拆分或生成空任务。
- 重要、高风险、跨模块架构任务交 Codex；分配表显式列出需 Codex 审核的风险项、负责人和通过条件，无则写“无”并说明判断依据。可按迁移/旧数据、契约变更、跨模块一致性等实际影响识别风险。
- 不要求 Codex 亲自开发或重复运行常规任务的完整测试；独立测试者执行必要边界、回归和集成检查，Codex 对列明风险做必要审核。
- 首次实施或修复仍未达到产品验收标准时，向 Codex 提交 Task/基线、实际 diff、失败用例与命令/退出码/证据、缺陷影响和已尝试方案，由 Codex 接管或调整方案，不连续盲目重试。环境未就绪或脚本错误导致的失败单独处理，不算产品实施/修复失败。
- 失败记录分为环境失败、测试脚本错误、产品缺陷；无法归类时标为待诊断，保留证据。脚本修正后的重试不计为产品修复失败，恢复后仍须实际验证产品行为。
- 可以独立执行且有实际收益的工作项尽量并行；存在依赖明确串行链，不为凑齐三个 Agent 强拆，不制定未经验证的固定模型能力排名。结合实际能力、上下文、成本及验证成本判断。
- 各 Agent 只读取自身 Task 必需阶段条款与代码；已读且未变的内容不重复加载，依赖遗漏按根规则补读。Codex 审核实际 diff 和必要证据，不重复常规全量测试或要求无收益的多份报告。
- 紧密依赖、共享文件和共享测试资源按需串行；开发者交付后停止写入，再交独立测试者。Codex 接管时先交接原写入者与资源，遵守最多三路及同目录单写者规则。

### 卡点识别与任务交接

- 同一问题经过两次实质不同的修复尝试仍失败，或调试 20～30 分钟没有有效进展，触发卡点预警。实质不同指有不同排查假设或修复方案，重复执行同一命令不算新方案；有效进展以定位缩小、获得新证据或验证假设为依据。本机制不延后上方首次产品实施 / 修复失败的升级要求。
- 出现上下文混乱、重复犯错、循环尝试，或需要超出授权范围的修改时，立即停止无效尝试并报告；未经批准不做超范围修改。环境失败、脚本错误与产品缺陷仍分开记录。
- 预警后先总结错误、已尝试方案及证据，标明已证实无效的方法；只有具备明确的新排查方向且在有效权限内时才继续，不重复盲试。没有新方向时报告卡点，等待 Lead 判断。
- Codex Lead 判断由原 Agent 继续、新对话继续、切换 Agent，还是提交用户决策；新增权限必须由用户批准。需要移交时生成下方简短 Blocker Handoff，执行提示词的对话与独立性规则仍按 §4。

```text
Blocker Handoff
问题：Task／名称、复现条件、影响与卡点原因
尝试记录：实质不同的方案、各自结果、已证实无效的方法
关键错误：错误摘要、失败分类及可访问证据路径，不含凭据或私人数据
Git 状态：工作目录、实际分支、HEAD、未提交／未跟踪改动及其归属
测试结果：实际命令、退出码、关键场景；区分本轮实测、引用证据与未验证项
未完成工作：剩余事项、暂停的写入与待协调资源
建议方向：新排查假设、所需证据及建议接续方式，供 Lead 判断
有效权限：已获授权的修改范围、环境／数据库／端口及 Git 权限；新增需求单列待批准
```

- Handoff 不是新的开发授权；交接前后不擅自 commit、merge、reset、删除修改或操作其他 Agent 的 Worktree。保留现有改动，写入责任和共享资源先协调交接，原授权、分工及安全规则不因 Handoff 自动改变。
- 接手 Agent 先只读核对实际代码、Git 状态、环境和证据，不盲信历史结论，不重复已证实无效的方法；基线或权限不符时报告，再决定后续动作。
- 正常完成的 Task 不额外生成 Handoff；只有发生卡点、换 Agent 或跨会话接管时生成必要交接，复用已有可访问证据，不另建重复状态文档、卡点登记系统或自动调度。

## 3. 新开发 Task 的标准流程

1. **只读检查**：始终读根 `AGENTS.md`、适用角色规范及本文件；按根 `AGENTS.md` §2 读取当前任务相关阶段章节和所需历史依据，再检查相关代码。核对 Task 范围/状态/前置验收、Git 分支/HEAD/已有改动/Worktree，以及实际环境与测试资源。不依据提交标题推断验收完成。
2. **方案与依赖**：确定最简单可行方案、接口与数据流、风险和必要文档修订。重大变化按根规则交用户决定；不擅自改变产品/API/架构。
3. **必要拆分**：保留原 Task ID、范围、依赖与 DoD；子任务 ID 用原 ID 的后缀，如 `S2-T08-A`。拆分不新增阶段功能。
4. **输出分配表**：使用下表，为每个子任务给出可核验标准和分配理由；预计路径在检查后具体化。
5. **明确串并行**：列出必须串行的链和能并行的组；同时交付工作区/分支基线、文件责任、资源表及 Git 权限。无并行收益时明确串行。
6. **输出执行提示词**：按 §4 分别生成开发、修复或独立测试的完整可复制文本；每份先标明 Agent / 模型、用途、对话建议及一句原因，再填写路径、约束、风险审核项、交付与实际测试命令。
7. **确认后实施**：默认先停在方案/提示词交付，用户确认开始后才修改代码；各 Agent 按已确认分工执行，Codex 按需介入。用户此前明确授权的实施范围继续有效，不重置正在进行的 Task。
8. **测试、审核与整合**：局部验证 → 获授权提交或 diff 交付 → 独立测试及必要集成/回归 → 列明的 Codex 风险审核 → 按权限整合及受影响复核 → 技术交付 → 用户最终接受。

方案交付必须包含七项：① Task 目标和前置依赖；② 推荐 Agent 人数及理由；③ 分配表（开发者与独立测试者）；④ 各 Agent 分支、Worktree、文件责任和资源表；⑤ 串并行依赖关系；⑥ 各 Agent 可直接复制的完整执行提示词；⑦ 测试、风险审核、Git 整合和交付安排。只有两个适合并行的工作项就推荐两个，不要求第三个参与；无并行收益可推荐串行。

分配表：

| 子任务 ID | 输入 / 输出 | 开发者 / 独立测试者 | 前置依赖 | 允许文件/模块 | 验收标准 | 交接方式 | Codex 风险审核项 / 负责人 | 分配原因 |
|---|---|---|---|---|---|---|---|---|
| 填实际 ID | 填已有输入与具体产出 | Codex / WorkBuddy / DSH，明确两种角色 | Task/子任务和所需证据 | 填允许路径 | 填可核验行为/测试 | 停止写入、交付 diff/提交和证据 | 填风险和通过条件，或“无”及依据 | 按 §2 说明 |

不在多个角色文件重复维护 Task 状态；实际执行记录由 Codex 按需同步到既有任务计划/验收记录。
既有明确授权与分工继续有效，S2-T07 不因配置调整重分配或重启；新增配置不授权后续 Task，也不授权实际调用 Agent。

## 4. 开发 / 修复 / 独立测试可复制执行提示词

以下是模板。Codex 下发时必须替换全部占位项、删除不适用条目；多个任务分别生成，不能只发模板或要求对方猜范围。

### 对话选择与轮次

每份提示词前必须标明使用 Agent 与模型（按 §1 配置）、执行端与模型核对状态、用途（开发 / 修复 / 独立测试）、对话建议（新开 / 继续）及一句建议原因；模板开头信息随提示词一并交付。

- “轮次”是一次完整执行 / 测试及结果交付，不按工具调用或普通消息计数；依据可核实交付记录，按同一功能、同一执行角色累计，不因新开对话虚构或重置已有次数。
- 同一功能、同一执行角色，累计 1～4 轮默认继续原对话；第 5 轮按上下文混乱、重复失败和任务范围判断，无明显问题可继续；超过 5 轮默认新开。不同功能默认新开。
- 独立测试的对话隔离优先于上述默认继续规则：使用未参与该次实现的新对话，即使功能相同也不沿用开发者对话；更换用途不等于获得独立性。
- 用户明确指定继续或新开时，以用户要求为准；若指定沿用参与实现的对话进行测试，应如实标注独立性未满足，不把该轮测试称为独立验收。
- 轮次无法确定时，在建议原因中简短说明所依据的功能、角色、可见交付记录或上下文状态，不虚构精确次数。轮次建议不改变 §2 的失败升级规则，也不为节省 Token 省略必要验证。

### 新对话自包含要求

新对话提示词必须包含目标、工作目录、实际分支与基线检查、修改范围、已有结果、剩余问题、验收标准、环境及 Git 权限；已有结果和剩余问题无则明确写“无”。证据给出可访问路径与必要摘要，明确已通过 / 失败 / 未验证项，不依赖“参考上个对话”才能执行。
分支、HEAD 和未提交 diff 以实际只读检查为准；无法预先核实时写明待核实与具体检查步骤，不填猜测值。新开对话不自动创建聊天、切换工作区或授予实施 / Git 权限。

## 5. Git、Worktree 与资源协调

### 工作区与权限

- main 原则上作为集成分支。每个同时写代码的 Agent 必须使用自己的 Git 分支和 Git Worktree；Codex 写代码时同样遵守。一个 Agent 可以串行在同一任务分支完成多个子任务。具体允许文件与模块由 Codex 明确。
- 开始前用 `git status --short --branch`、`git rev-parse HEAD`、`git branch -vv`、`git worktree list --porcelain` 核对现状；优先复用合适的既有 Worktree，不为形式新增目录。
- 既有 `task/...` 分支保留；新增 Codex 分支默认 `codex/<task-name>`，用户指定名称优先。分支前缀不决定任务权限。
- 同一工作目录同一时刻只有一个修改者；共享文件、迁移链和有实现依赖的修改按顺序交接。Worktree 只隔离文件，不隔离端口、环境变量、数据库和 Git 共享元数据。
- 分配方案明确哪些 Git 操作获准：建/复用分支和 Worktree、本地 commit、整合到 main 分别列出。确认开始只授权方案中列明的操作，未列明的不推定批准；已明确批准不重复询问。
- 局部验证后按授权提交或交付 diff；独立测试通过、列明风险审核完成后，再按已确认权限整合。整合负责人在方案中明确；Codex 介入时审查实际差异与风险，不重复常规完整测试。必要整合回归通过后交付技术结论，用户最终接受；未授权提交/整合时交 diff 并标明待办。
- push、tag、删分支、清理 Worktree 单独按用户授权处理，不把 Task 完成视为自动许可。只提交任务文件，排除 .env、凭据、私人数据、私密 Prompt、helper 和构建产物。
- 不用 reset --hard、强制切分支或整目录复制覆盖来解决协作冲突；Codex 审查冲突并保留必要改动。

### main 整合后的显式同步

main 合并不会自动改变其他 Worktree 的文件。Codex 先确认对方停止写入、工作已保存、工作区干净，再由目录所有者更新对应分支：

- 已完成、无需保留独立提交的任务分支，可在该目录运行 `git merge --ff-only main`；
- 仍有独立提交、无法快进时，由 Codex 协调 `git merge main`，审查冲突并重新做受影响验证；不自动 rebase 他人的工作；
- 新任务从已验收的集成基线开始。更新后报告分支/HEAD、状态及必要检查；不得把旧 Worktree 当成已同步。

以上命令用于已确认的更新操作，不在文档修改轮执行；不能覆盖未提交改动，也不在已有 main checkout 时让另一个 Worktree 同时检出 main。

### 每轮资源表

规划时至少填写：

| 工作项/所有者 | 目录/分支/基线 | 文件责任 | 前端/后端端口 | 前端 API 地址配置 | 后端目标库配置/测试库 | 共享资源与串行安排 |
|---|---|---|---|---|---|---|
| 填实际工作项 | 填实际值 | 精确路径 | 检查空闲后分配 | VITE_API_BASE_URL | DATABASE_URL 的配置方式与库名，不贴密码 | fixture/迁移/测试库独占者 |

- 每个服务使用独立端口和进程环境；不复制覆盖真实 .env，不输出带密码的连接串。浏览器写入前证明实际连接测试库。
- 复用已有 PostgreSQL，默认不启动 Compose、不动既有 5173/8000/5432 服务；确需变化先纳入方案授权。
- 可用独立测试库并行时，必须确认迁移版本和测试 fixture 支持该库；当前固定指向 seekjournal_test 的后端 pytest 同一时刻只能一个流程使用，不能假定设置 DATABASE_URL 就能改它。
- 无法隔离的测试/迁移/UI 写入排队执行；个人库 seekjournal 默认只读，真实库升级单独授权。每轮只清理自建对象并核对无残留。
- Codex 负责协调共享文档；同步前核对基线与对方改动，只同步授权变更，不覆盖整个文件树。历史 T03/T04 的路径/端口/库见既有记录，不能自动用于新 Task。

## 6. 统一验收与完成条件

开发者与独立测试者使用同一清单完成技术交付；Codex 对显式列出的风险项、升级任务及获授权整合做必要审核：

| 检查 | 必要证据 |
|---|---|
| 需求与范围 | 实际 diff/行为映射原 Task 和验收标准，无擅自扩张 |
| 测试与回归 | 适用局部测试、必要集成/回归、人工步骤；命令、退出码、结果和限制 |
| 架构与重复 | 遵守权威架构/API，跨模块一致，无明显重复实现或无理由依赖 |
| 数据与环境 | 迁移/旧数据保护、正确目标库、测试无残留、服务收尾 |
| 文档 | 需要更新的契约/运行说明/执行记录已由责任人同步，历史证据保留 |
| Git 与 Worktree | 分支/HEAD/工作区/提交/整合符合授权；需使用的其他分支显式更新或标明仍旧基线 |

开发者自测不能替代另一 Agent 的独立测试；独立测试者检查实际差异并独立运行必要测试，记录基线、命令、退出码、证据及失败分类，按下方统一简报交付。
执行独立性要求独立会话、独立执行且测试者未参与该次实现；WorkBuddy 和 DSH 即使均调用 DeepSeek V4.1 Flash，也可满足此要求。模型多样性指不同模型的交叉验证，换客户端不等于换模型，同模型测试不能声称具备模型多样性。报告分别注明两者是否满足；重要风险由 Codex 做必要独立审核或定向验证，不因执行独立而免除原专项门禁。
常规任务无需 Codex 重复全量测试；需要 Codex 审核的风险项及状态必须显式列出，未完成前不能宣布验收完成。Codex 自己实施的任务也安排独立测试；用户最终接受，共享权威文档仍由 Codex 同步。

只有全部必要验收、约定的整合以及原 Task DoD 完成，才能宣布 Task 完成。
代码已写/局部测试通过/等待提交或整合是进度状态；未完成检查、风险和未获权限的操作必须明示。
用户最终接受和 Stage 整体验收按原阶段计划执行，单个 Task 完成不等于 Stage 完成。

### 统一交付简报

开发、修复与测试均使用以下八项格式，默认最终输出约 300～500 字，复杂任务只增加必要内容，让用户可直接复制给另一 Agent 做简单 review。必要命令、路径、失败说明和审核条件不能为控制字数而删除。

```text
任务：ID／名称（注明开发、修复或独立测试角色）
基线：实际分支、HEAD、工作区状态（未提交改动纳入待测基线）
结果：完成／通过／未通过／部分通过（注明自测或独立测试结论及审核、用户接受状态）
改动：文件及主要行为；测试者无改动则注明“无改动”
验证：本轮实际命令、退出码、关键场景结果；引用证据单独标明，未执行不写通过
问题：缺陷、未验证项、阻碍、待审核项；没有则写“无”；失败写复现条件、影响、下一步及失败分类
收尾：实际 Git 状态与待提交／整合情况；涉及服务或数据库时补自建服务、数据及清理结果
证据：一个可访问的报告或证据目录路径（优先绝对路径）
```

- 简短输出不减少必要测试，不逐条复述过程，不堆叠历史测试数量；区分自测 / 独立测试、本轮实测 / 引用证据，报告基于实际基线与命令结果。
- 失败必须说明复现条件、影响和下一步；环境失败、脚本错误、产品缺陷分别记录，不把脚本重试算作产品修复失败。未验证项与必要风险审核不能压缩掉。
- 简报与证据均不输出凭据、连接串或私人数据；详细日志按需保留在本地证据目录并脱敏，简报给出可访问路径，不以不可访问的旧对话代替证据。
- 关键技术变化按根规则保留最多 1～3 个学习点，可在“改动”中简述新增内容、原因与数据流；常规文案和小修复不强制长篇学习说明。
- 简报缩短不省略用户最终接受、必要审核、独立测试或约定整合条件；技术交付与最终验收状态必须区分，未满足门禁不能写成验收完成。
